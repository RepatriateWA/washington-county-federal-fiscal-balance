# EPS-001 Architecture

**Evidence Package Standard (EPS-001)**

Version: 1.0 (Draft)

Project:
Washington County Federal Fiscal Balance Project

---

# 1. Purpose

The Evidence Package Standard (EPS-001) defines a reproducible, transparent,
and auditable framework for publishing certified data products generated by
the Washington County Federal Fiscal Balance ETL system.

EPS-001 was developed to ensure that every published dataset can answer four
fundamental questions:

1. What data were produced?
2. How were they produced?
3. Can the process be independently reproduced?
4. Has anything changed since certification?

Rather than relying on trust, EPS-001 relies on evidence.

Every certified dataset is accompanied by machine-readable and human-readable
artifacts documenting the provenance, validation, certification status, and
technical characteristics of the published results.

---

# 2. Guiding Principles

EPS-001 is built upon several engineering principles that govern every design
decision throughout the project.

## Measure First. Explain Later.

The project intentionally separates evidence collection from interpretation.

Data are collected.

Evidence is validated.

Certification is performed.

Interpretation occurs only after reproducible evidence has been established.

This separation minimizes confirmation bias and encourages objective analysis.

---

## Evidence Over Assertion

Claims should be supported by measurable evidence.

Whenever possible, evidence should be reproducible from publicly available
source data.

---

## Transparency Over Opacity

Every processing step should be discoverable.

No hidden calculations.

No undocumented transformations.

No unexplained assumptions.

---

## Reproducibility Over Convenience

Any qualified analyst should be capable of rebuilding a certified Evidence
Package using:

* Source data
* Published ETL software
* Versioned schemas
* Public documentation

Reproducibility is considered more important than execution speed.

---

## Automation With Human Review

Certification decisions are generated automatically.

Certification reports are reviewed by humans.

Automation improves consistency.

Human review provides accountability.

```
 Manifest   Certification   Metadata
                 │

                 │

```

The EvidencePublisher serves as the orchestration layer responsible for
producing the complete package.

Each builder produces exactly one artifact.

# 4. Package Lifecycle

An Evidence Package progresses through several distinct phases.

## Phase 1

Raw source acquisition

Examples:

* IRS SOI
* Census
* Treasury
* USAspending

---

## Phase 2

ETL processing

The ETL pipeline imports, normalizes, and validates source information.

---

## Phase 3

Validation

Automated validation rules verify:

* completeness
* integrity
* consistency
* business rules

Validation does not certify the data.

Validation produces evidence used during certification.

---

## Phase 4

Certification

Certification evaluates validation results.

A certification status is assigned:

* CERTIFIED
* NOT_CERTIFIED
* ERROR

---

## Phase 5

Publication

The EvidencePublisher creates the complete package.

# 6. Component Responsibilities

## EvidencePackage

Represents package identity.

Responsibilities:

* package identifier
* dataset name
* batch number
* certification state
* publication metadata

This object contains no file-writing logic.

---

## EvidenceWriter

Responsible solely for directory creation.

Responsibilities:

* create package directory
* create subdirectories
* return package path

No JSON generation occurs here.

---

## ManifestBuilder

Produces:

manifest.json

Responsibilities:

* package inventory
* artifact listing
* hashes
* publication metadata

ManifestBuilder never writes files.

---

## MetadataBuilder

Produces:

metadata.json

Responsibilities:

* runtime environment
* Git commit
* Git status
* software versions
* repository metadata
* provenance information

---

## CertificationBuilder

Produces:

certification.json

Responsibilities:

* certification status
* validation summary
* individual checks
* statistics
* version information

CertificationBuilder contains no file I/O.

---

## ReportWriter

Produces:

certification_report.txt

Responsibilities:

* human-readable certification summary
* validation results
* evidence overview

The report is derived entirely from certification.json.

Certification JSON remains the authoritative record.

---

## JsonWriter

Responsible only for serialization.

Responsibilities:

* UTF-8 encoding
* Unix line endings
* deterministic formatting

No business logic is performed.

---

## EvidencePublisher

Coordinates the publication process.

Responsibilities:

1. Create directories
2. Build artifacts
3. Serialize artifacts
4. Publish package

EvidencePublisher contains orchestration logic only.

# 7. Artifact Relationships

```
EvidencePackage
        │
        ▼
EvidencePublisher
        │
 ┌──────┼──────────────┐
 ▼      ▼              ▼
Manifest Metadata Certification
                     │
                     ▼
              ReportWriter
```

Builders are intentionally independent.

No builder depends on another builder.

This minimizes coupling and simplifies testing.

---

# 8. Separation of Concerns

EPS-001 follows the Single Responsibility Principle.

Builders build.

Writers write.

Publishers orchestrate.

Validators validate.

Schemas define structure.

This architecture minimizes unintended side effects while simplifying unit
testing and long-term maintenance.

---

# 9. Certification Philosophy

Certification does not imply that source data are perfect.

Certification indicates that:

* the ETL process completed successfully;
* required validation rules passed;
* certification criteria were satisfied;
* published artifacts accurately represent the processing results.

Certification concerns process integrity—not policy conclusions or analytical interpretation.

---

# 10. Versioning Strategy

Four independent version numbers are maintained.

## Evidence Package Version

Defines package organization.

Example:

EPS-001

---

## Schema Version

Defines JSON schema compatibility.

Schema evolution should preserve backward compatibility whenever practical.

---

## ETL Version

Identifies the software responsible for producing the package.

---

## Certification Version

Defines certification policy.

Certification policies may evolve independently of ETL software.

---

# 11. Reproducibility

A certified package should be reproducible from:

* identical source data
* identical ETL version
* identical certification rules

Differences should be explainable through version changes or source data updates.

---

# 12. Integrity

Future versions of EPS-001 will include:

* SHA-256 artifact hashes
* manifest verification
* optional digital signatures

These features provide cryptographic verification that package contents have not been modified after publication.

---

# 13. Testing Strategy

Each component is tested independently.

Examples:

* MetadataBuilder contract test
* CertificationBuilder contract test
* ReportWriter contract test
* EvidencePublisher integration test

Integration tests verify interactions between components.

Contract tests verify each component independently.

---

# 14. Future Roadmap

Planned enhancements include:

* SHA-256 artifact inventory
* Manifest finalization
* JSON schema validation
* Digital signatures
* Incremental Evidence Packages
* Parallel publication
* Web-based evidence browser
* Automated certification dashboards

These enhancements extend EPS-001 without changing its core architectural principles.

---

# 15. Conclusion

EPS-001 establishes a reproducible framework for publishing certified data products.

The architecture deliberately separates:

* evidence collection,
* validation,
* certification,
* publication,
* and interpretation.

This separation improves transparency, reproducibility, maintainability, and public trust.

The Evidence Package is intended to serve as a permanent, auditable record of the certification process, ensuring that future analysts can reproduce, verify, and evaluate published results using objective evidence rather than undocumented assumptions.

Ultimately, EPS-001 supports the broader mission of the Washington County Federal Fiscal Balance Project:

> Measure first. Explain later.
